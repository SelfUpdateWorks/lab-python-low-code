# Refactoring Notes – Meal Planner

## Baseline (original code)
- Vegetarian plan generated in 12.04s, "All checks passed", 7 recipes, 7 unique themes
- Test cases: omnivore/vegetarian/vegan/keto → all PASS
- Email Plan: took ~25s, then "Failed to send email: Connection unexpectedly closed"

## Issues Found
- [ ] **Security:** `app.launch(share=True)` creates a public URL; anyone could use the app on my API key for up to a week.
- [ ] **Bug (wrong plan + double cost):** `send_email_ui()` calls `generate()` again, so the emailed plan is a new one, not the one on screen, and it costs a second API call (~25s).
- [ ] **Silent failure / missing validation:** The shopping list is never checked against the recipes. In my run, Chickpeas (400g, Thursday) were missing, but the app showed "All checks passed".
- [ ] **Unhelpful error message:** The email error doesn't say where it failed, the real cause (placeholder credentials), or how to fix it.
- [ ] **Dead code:** SHOPPING_LIST_PROMPT (and self.shopping_parser in __init__) are defined but never used. They mislead the reader into thinking a separate shopping-list step exists.
- [ ] **Lost information:** ShoppingItem.used_in is requested from the model and validated, but format_shopping_list() and format_meal_plan_email() never show it.
- [ ] **Safety net:** Try starts after API call.  With a wrong API key, no Wi-Fi or a rate limit, the error isn’t caught: the app crashes and the user sees an ugly message (or nothing).
- [ ] **Fragile parsing:** The code-fence cleanup assumes the answer looks exactly like ```json {...} ```. If the model adds a sentence before the JSON or forgets the closing fence, a valid plan is rejected with a vague “JSON parsing error” that doesn’t say where.
- [ ] **Inconsistent output:** Success returns success, meal_plan, generation_time, error; failure returns only success, meal_plan, error. Any caller that reads result["generation_time"] without checking success first will crash with a KeyError.
- [ ] **Hardcoded secret:** EMAIL_SENDER and EMAIL_PASSWORD are typed into the config cell, while the API key correctly comes from .env. The notebook instructions (“Edit the values below”) invite users to paste a real Gmail app password, which would be pushed to GitHub. Both should be read from .env with os.getenv(), like the API key.
- [ ] **Repeated logic + inconsistent defaults:** “Empty textbox → default” is written by hand in 3 places (generate(), generate_plan_streaming(), send_email_ui()) with different defaults (“random diverse cuisines” vs “random”). The UI versions use .strip(), which crashes if the value is None. This should be one helper function, e.g. clean_input(value, default).
- [ ] **Hardcoded values / unused constants:** EXCLUDED_BASICS and DAYS are defined but never used. Instead, the same values are typed by hand in the prompt (“salt, pepper, oil…”, “EXACTLY 5”, “Monday-Sunday”) and in run_basic_validation() (5, 7). Changing a constant would not change the app consistently.
- [ ] **Duplicated / ineffective validation:** run_basic_validation() re-checks exactly what Pydantic already enforced (7 recipes, unique themes, 5 ingredients), so on a successful result it can never fail. The real gap, shopping list vs. recipes, is not checked anywhere, so “All checks passed” is shown even when ingredients are missing (Chickpeas in my run).
- [ ] **Silent failure – missing API key:** If .env is missing, os.getenv("OPENAI_API_KEY") silently returns None; the config cell shows ✅ and the crash appears one cell later as TypeError: str expected, not NoneType, which doesn’t mention the API key, .env, or how to fix it. Fix: check the key right after loading and stop with a clear message, e.g. “OPENAI_API_KEY not found – create a .env file with OPENAI_API_KEY=sk-...”.
- [ ] **User input ignored (anchoring):** The "Themes" field only works for cuisines that appear in the system prompt's example list. Tests: "Mexican" or "American" → moved to Monday, rest in example-list order; "German" or "Turkish" → completely ignored, week = first 7 themes of the example list (Italian … American). The example list in the system prompt anchors the model more strongly than the user's request.
- [ ] **Unvalidated field content:** The model sometimes puts preparation notes into `quantity` ("1 cup, sliced", "1, diced"), producing "1, diced Tomato" in the UI. Units are also inconsistent between runs ("tbsp" vs "tablespoons", "2 units"). Pydantic only checks that `quantity` is a string, not its format.




## Product improvements (out of scope for refactoring)
- Shopping list uses cooking units ("1 tsp thyme", "1/2 red onion"); a shopping list should use purchasable units (1 bunch, 1 onion, 1 jar).

## Priority

1. **Hardcoded secret** – because a real Gmail app password typed into the notebook would be pushed to GitHub with the next commit. A leaked password cannot be "un-leaked"; it gives strangers access to the email account. This is the only issue where the damage is permanent, so it comes first.

2. **Duplicated / ineffective validation** – because it gives users wrong information while telling them everything is fine. In my baseline run, Chickpeas were missing from the shopping list, yet the app showed "All checks passed". A user would go shopping, miss an ingredient, and lose trust in the app. A silent wrong answer is worse than a visible error.

3. **Silent failure – missing API key** – because the most common setup mistake (no `.env` file) produces a confusing `TypeError: str expected, not NoneType` one cell later, with no hint about the API key or how to fix it. Every new user or teammate will hit this first, so a clear message here saves the most time.

**Next in line:** `share=True` (public URL using my API key – already fixed for the baseline run) and the email button sending a different, newly generated plan at double cost.

Product improvements:
- "Themes" input conflicts with the unique-themes rule: a user asking for "Italian" gets only one Italian day; an all-Italian week is impossible. The UI doesn't explain this.
